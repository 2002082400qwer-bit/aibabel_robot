# MOT1 行程中段抖动分析

分析日期：2026-10-08。用户确认抖动发生在行程中间；目标速度及实机串口数据尚未提供。

分析依据是当前工作区源码，未读取设备内固件，也未进行实机验证。本轮只记录分析，不修改电机控制代码。

## 判断

优先怀疑速度闭环输出波动：未经滤波的测速值进入较强的微分项，采样间隔变化可能进一步放大波动；2200 的运行 PWM 下限也可能使某些目标速度无法达到。现有证据能证明这些代码机制，尚不能确定哪一项触发了实机抖动。

## 1. 微分项会放大测速波动，实际增益与注释不一致

`USER/Sourse/mot1.c:121` 起定义缩放 100、Kp 100、Ki 2、Kd 100，因此代码中的有效增益分别为 1.00、0.02、1.00。第 124 行注释仍写 Kd=0.50，与实际执行值不符。

第 158～165 行直接使用原始速度误差的二阶差分，增量公式为：

```text
ΔPWM = (e[k] - e[k-1]) + 0.02 × e[k]
       + (e[k] - 2 × e[k-1] + e[k-2])
```

第 292～296 行将本周期编码器脉冲直接换算为速度，没有速度或微分低通滤波。默认每度脉冲缩放值为 200 时，每个 50 ms 窗口多一个脉冲，速度读数就增加 10；标定后的实际分辨率取决于 `PulseNumPerAngle`。

提取当前 C 控制函数，复用工程已有函数提取器，进行有界 JavaScript 诊断。设目标速度为 900、内部 PWM 初值为 3000、误差历史为 0，并保持远离目标及限位。输入每周期脉冲为 90、80、100、80、100、80、100，速度换算值为 900、800、1000、800、1000、800、1000：

| 诊断用 Kd 宏值 | 后续反复交替的 PWM | 两个输出之差 |
| --- | --- | --- |
| 100，当前源码 | 3302 / 2700 | 602 |
| 50，仅诊断时替换 | 3202 / 2800 | 402 |
| 0，仅诊断时替换 | 3102 / 2900 | 202 |

当前参数下，这组人为输入造成约 12.5% PWM 满量程的反复变化。该计算说明 D 项的放大作用；输入的 900、800、1000 是举例值，不是用户实测数据，也不是闭环电机稳定性仿真。不能仅凭增益数值断言电机必然不稳定。

TI 的电机控制库文档说明，微分通道会放大高频噪声，可在该通道加入数字滤波。该资料支持上述机制，不直接提供本机电机的整定参数。[TI DMC 数学库文档，第 93 页](https://e2e.ti.com/cfs-file/__key/communityserver-discussions-components-files/171/DMC-MATH_5F00_v13.1.pdf#page=93)

## 2. 实际采样间隔变化时，固定 50 ms 换算会产生虚假速度波动

`USER/Include/motor.h:14` 定义控制周期为 50 ms。`USER/Sourse/FT32F10x_it.c:118` 在中断中增加计时值，但实际 PID 和脉冲读取在主循环执行。

`USER/Sourse/mot1.c:268` 判断周期到期后，第 270 行只从计时值扣除 50；第 292 行却始终以固定 50 ms 换算读到的全部脉冲。如果某次执行延迟，测速窗口会变长，下一次追赶执行的窗口又可能变短。

仍设电机匀速，每 50 ms 产生 90 个脉冲。以当前参数和相同诊断初值计算：

| 相邻两次读取的实际间隔 | 读到的脉冲 | 代码算出的速度 | PWM 输出 |
| --- | --- | --- | --- |
| 50 ms | 90 | 900 | 3000 |
| 75 ms | 135 | 1350 | 2200 |
| 25 ms | 45 | 450 | 4459 |
| 50 ms | 90 | 900 | 2659 |

这说明采样间隔变化可以在实际匀速时产生很大的 PWM 波动，尚未证明设备实际发生了上述延迟。

主循环在 `USER/Sourse/sys.c:260` 依次执行其他服务，最后才调用 `MotorService()`。ToF 的同步 I²C 调用存在忙等待和最多 100 次重试（`USER/Sourse/tmf8806_shim.c:231`、`:242`），是需要测量的阻塞来源。当前启用的读取分支还存在没有超时的等待（`USER/Sourse/i2c.c:214`）。这些代码存在不代表本次运行已经出现总线错误。

MOT1 每周期有 6 条同步串口打印，但串口实际配置为 921600 波特率（`USER/Sourse/uart.c:155`）；百余字节在线路上的发送时间约为 1～2 ms，不能仅凭打印数量认定它单独导致几十毫秒延迟。应测量总执行时间及中断占用。

## 3. PWM 下限可能阻止控制器降到目标速度

`USER/Sourse/mot1.c:128` 定义运行 PWM 下限为 2200，第 314～316 行同时将内部输出和实际 PWM 钳位到这个值。它占 4800 数值满量程的约 45.8%。

如果当前负载下 PWM=2200 时电机仍快于目标速度，控制器就无法继续降低驱动力；测速波动时，微分项还可能让输出从下限反弹。是否出现这种情况，必须测量 PWM=2200 时的速度，不能直接认定下限过高。

## 4. 指令更新也可能造成行程中间停顿、重新启动

`USER/Sourse/mot1.c:517` 仅过滤角度和速度都完全相同的任务。任一值改变，都会重新启用任务；第 528 行起的任务处理会先刹停当前运动，再启动新运动。因此上位机若连续改变目标角度或速度，会出现中途反复刹停和启动。

实机日志若频繁出现 `m1 task`、`m1pulsebrake`、`m1 stop`，应先核对收到的任务值及更新频率。相同指令重复发送已被过滤，不能把普通重复下发直接当作原因。

## 建议的验证顺序

1. 固定一次目标角度和速度，观察中段 `M1.CurVel`、`pwm` 和任务/刹停日志。核对目标有没有改变、PWM 是否反复大幅变化。
2. 在相同速度、负载及其他参数下，仅把 Kd 宏从 100 改为 0 做一次对照。抖动若明显降低，说明微分通道参与了问题；这不是最终整定结论。再单独评估低通滤波和较小 D 项。
3. 测量两次 `Mot1ReadEncode()` 的实际间隔和原始脉冲数，确认读数波动是否来自窗口长度。若间隔不稳定，应采用确定的采样窗口或按实际时间换算；Ki/Kd 的周期假设也要一并核对。
4. 单独测量 PWM=2200 时的稳态速度和启动能力，再判断运行下限是否合适。
5. 如在匹配速度、负载的固定 PWM 对照下仍抖，进一步检查编码器波形、供电、驱动板及机构摩擦/齿轮间隙。

普通长行程的末端减速只在剩余脉冲进入最多 300 脉冲窗口后生效，且目标速度需大于 1000（`mot1.c:304` 起）。短行程窗口为目标脉冲的一半，故“中间”若指很短行程的后半段仍需核对剩余脉冲；当前优先级仍是速度反馈、采样时序和任务更新。启动基准只保存在内部，首个 PID 周期前不立即写 PWM，这只能解释启动迟滞，不能单独解释持续中段抖动。

本轮诊断仅验证了有界输入下的算式和分支，未模拟硬件中断、电机动力学或 C 整数溢出；未生成、烧录新固件，未声称问题已修复。原有三路电机及 `context.jsonl` 的未提交修改保留。
